# Hifz — project guide

A calm, focused Qur'an **memorization** (hifz) companion PWA. Sister app to
**Daily Tilawah** (a reading app) — shares its technical foundation (Qur'an
data layer, font pipeline, theming, i18n pattern) but is a separate,
standalone product with its own identity: emerald/amber instead of
navy/gold, and a tracker rather than a page-a-day reader.

Philosophy: focused and encouraging, never anxiety-inducing. No leaderboards,
no guilt-tripping. Protect the calm — check before adding anything that would
make it feel heavy or cluttered.

## Stack
- React 18 + Vite + Tailwind + react-router-dom. PWA (`public/manifest.webmanifest`, `public/sw.js`).
- No test suite. Verify with `npm run build`. There is **no lint script**.

## Hosting
- **Live**: https://hifz.danisheddie1405.workers.dev/ — **Cloudflare Workers (static assets)**: root `wrangler.toml` (`[assets] directory = "./dist"`), build command `npm run build`, deploy command `npx wrangler deploy` — set up via the dashboard's git-connected "Create a Worker" flow, not classic Pages (Cloudflare's newer unified flow puts git-connected static sites under Workers too). Auto-deploys on every push to `main`.
- SPA routing via `wrangler.toml`'s `not_found_handling = "single-page-application"`. Do NOT add a `public/_redirects` file (that's the classic-Pages mechanism) — it's rejected at deploy time as a redirect loop ("Line 1: Infinite loop detected... strip `.html` or `/index`") when Workers static-assets also has `not_found_handling` set, since the two now do the same job and conflict. Do NOT re-add a GitHub `404.html` either — it mangles URLs on Cloudflare.
- The temporary GitHub Pages preview workflow (`.github/workflows/deploy.yml`) has been removed now that Cloudflare is the real deploy target — don't re-add it. `vite.config.js` no longer needs a `base` override either, now that there's no `/hifz/`-subpath GitHub Pages build to account for; it serves at `/` unconditionally.

## Cloud sync (`worker/`, optional — off until deployed)
A Cloudflare Worker + KV backend for "Back up & sync" (Settings → Back up & sync), mirroring Daily Tilawah's `worker/`/`cloudSync.js` pattern minus the prayer-reminder machinery (not a Hifz feature — no cron, no push, no `prayer.js`/`push.js`). Deploy steps: `worker/DEPLOY.md`.
- **Inert by default**: `src/config.js` ships with `WORKER_URL`/`GOOGLE_CLIENT_ID` empty, exactly like Tilawah's pre-deploy state. `SyncSettings` shows a "not connected yet" message and disables the create/link buttons until `WORKER_URL` is set; `GoogleSignIn` renders nothing until both vars are set.
- **Two credential types**, either works with `/sync/pull` and `/sync/push`: a generated **sync code** (`{ code }`, ~60 bits of entropy, the credential itself) or a **Google session token** (`{ token }`, issued by `/auth/google` after verifying an ID token via Google's `tokeninfo` endpoint, 180-day TTL). `src/utils/cloudSync.js` picks whichever is active (Google takes precedence).
- **Merge strategy is per-surah, not linear**: Tilawah's `mergeSnapshots` takes the max of linear counters (pages read, streak) because progress there is strictly ordered. Hifz's status isn't (`memorizing` and `revision` aren't comparable), so `mergeSnapshots`/`mergeSurahStatus` instead unions the two devices' `hifz:surahStatus` maps key-by-key, and where **both** sides touched the same surah, last-write-wins by `updatedAt`. `hifz:settings` follows whichever snapshot's `_updatedAt` is newer.
- `schedulePush()` (debounced ~2.5s) is called after every mutation that should sync: `SurahDetail`'s status change, `RevisionScreen`'s "mark confident", `NotesEditor`'s autosave. `syncNow()` (pull + merge + apply + push) runs once on app boot (`App.jsx`) — a no-op when sync isn't configured or linked.
- **Verified against a real local Worker**, not just read through: ran `wrangler dev --local` (Miniflare simulates KV, no Cloudflare account needed), pointed `config.js` at it, and drove two independent browser contexts end-to-end — Device A marked two surahs and created a code; Device B (different surah already set) linked that code and correctly ended up with the union of both; Device A then hit "Sync now" and picked up Device B's surah too. No data lost either direction. `config.js` was reverted to empty afterward — nothing points at the local test server in committed code.

## Personalization (onboarding + dashboard greeting)
First launch is gated by `isOnboarded()` (`src/utils/storage.js`, key `hifz:onboarded`) — `App.jsx` renders `Onboarding` instead of the router until it's set.
- `Onboarding` (`src/components/Onboarding.jsx`) is a 4-step wizard: welcome → name (required, so the dashboard has something to greet) → an optional quick-start surah picker (Juz 30, surahs 78–114 — the shortest surahs and where most people's hifz journey actually starts; picking any marks them `memorized` immediately, so the dashboard isn't empty on day one) → a bismillah screen before `completeOnboarding(name)` writes both the name and the onboarded flag in one call. Matches Tilawah's step-wizard pattern (progress dots, back button) minus its goal/starting-point steps, which don't apply here.
- The name is a first-class syncable field, not just local flavor: `hifz:userName` is in `cloudSync.js`'s `SYNC_KEYS`, and `mergeSnapshots` prefers a non-empty name, letting the newer snapshot win only when both sides have one set (so linking a fresh device never blanks a name already chosen elsewhere).
- `Home`'s greeting (`greetingMessage()`) is deliberately state-based, not time-based: it never mentions elapsed time or a count of "overdue" surahs, in keeping with the "no guilt-tripping" philosophy — it reads as "you have surahs ready for a gentle revisit," not "3 surahs overdue for 12 days." The four states, checked in order: nothing tracked yet → one surah in progress (names it) → several in progress → fully caught up.
- The name can also be edited any time from `Settings` (a plain text input above the language picker), which calls `schedulePush()` on change like every other syncable mutation.

## Qur'an data (local-first, with live fallback)
- `npm run build-data` (`scripts/build-quran-data.mjs`, copied from Daily Tilawah) writes `public/data/`: `meta.json`, `page/<1..604>.json` (QCF v2 glyph lines + per-verse words/text), `translation/<edition>.json`, `ayah-pages.json`. See `scripts/DATA.md`.
- `src/utils/api.js` is **local-first**: `getPage`/`getMushafPage`/`getAyahPage` use `public/data/` when present, else fall back to live APIs (quran.com for glyphs, alquran.cloud for translations). Audio streams from islamic.network CDN via `audioUrlAt(edition, globalNumber, bitrate)`; `AUDIO_BITRATES` (128/64/192) is the fallback chain SurahDetail tries in order, since not every reciter is hosted at every bitrate.
- `getSurah(number, opts)` and `listSurahs()` are Hifz-specific additions on top of the page-based data layer: `getSurah` walks the mushaf pages a surah spans (via `SURAH_PAGES`/`SURAH_AYAHS`) and filters ayahs by surah number, so the app can be surah-centric even though the underlying bundle is organised by page.
- QCF per-page fonts load from jsDelivr (`mushafFontUrl`, `src/utils/fonts.js`). The KFGQPC Uthmanic Hafs unicode font is self-hosted (`public/fonts/`), used as the fallback whenever a page's glyph font hasn't loaded (also the only rendering path in this dev sandbox, since the jsDelivr CDN is unreachable through the sandbox proxy — works normally in production/browsers with real network access).

## Offline caching (`public/sw.js`)
The whole app works offline after one online visit, not just pages the user happened to open:
- **Precached in the background on `activate`** (fire-and-forget, doesn't block install/activation): `meta.json`, `ayah-pages.json`, all 604 `page/N.json` files, and every translation edition — the full Qur'an dataset, ~14MB of text. The edition list is hardcoded in `sw.js` (`TRANSLATION_EDITIONS`) and must be kept in sync with `TRANSLATIONS`/`TRANSLITERATION` in `src/utils/api.js` by hand, since the service worker is a plain script and can't import app modules.
- **Deliberately NOT precached**: the QCF per-page glyph fonts (external jsDelivr CDN) — still cached lazily as pages are viewed via the existing cache-first rule; an offline, never-visited page falls back to the self-hosted KFGQPC font instead (bundled in the app shell, needs no network), so text is never unreadable offline, just not in the exact per-page mushaf glyph. Audio (streamed, not meant to be stored) and tafsir (a third-party API with no bulk-fetch endpoint — precaching it for all 6236 ayahs would mean thousands of requests per install) also stay online-only.
- `src/main.jsx` calls `navigator.storage.persist()` on boot (best-effort) so the browser is less likely to evict the cache under storage pressure.
- Cache is versioned (`hifz-cache-v2`); bump the version string whenever the caching strategy changes so `activate` cleanly replaces the old cache.
- Verified directly: built the app, served it, waited for the precache to reach 612 cached entries, went offline, and opened a surah never visited in that session — it rendered fully (Arabic, translation, all controls) from cache alone.

- `src/utils/cloudSync.js` — sync + `mergeSnapshots` (smart merge; per-surah union, see "Cloud sync" above). `SYNC_KEYS` lists synced keys.
- `src/config.js` — `WORKER_URL`/`GOOGLE_CLIENT_ID`, empty until the Worker is deployed (see "Cloud sync" above).
- `src/utils/progress.js` — `computeProgress()`: turns the status map into dashboard stats (% memorized by ayah count, Juz completed, surahs memorized). Juz completion is computed at ayah granularity (via `getAyahPagesIndex` + `juzForPage`) since a surah can straddle a Juz boundary even though status is tracked per-surah.
- `src/utils/statusStyle.js` — color classes per status (badge/dot/active/ring), shared by `StatusBadge`, `StatusControl`, and the surah-index number-circle ring.
- `src/utils/dateUtils.js` — `daysAgo()` and `formatLastRevised()`, shared by the dashboard's revision preview and the full `RevisionScreen`.
- `src/utils/tafsir.js` — per-ayah tafsir from the quran.com API, cached forever in localStorage (the text never changes). Resolves the English tafsir resource id dynamically (prefers Ibn Kathir, then al-Jalalayn, then whatever's first) rather than hardcoding one; strips the API's HTML to plain text via a detached-element `textContent` read (decodes entities, never inserts untrusted HTML into the page). No bundled/local tafsir data — this feature is online-only and degrades to an inline "couldn't load" message when the API is unreachable, same as the QCF glyph font CDN.
- `src/utils/i18n.jsx` — UI strings in **en / ms / id**. Every user-facing string must have a key in all three.
- `src/utils/fonts.js` — lazy-loads QCF v2 per-page glyph fonts, cached on `document.fonts`.
- `src/utils/theme.js` — applies the `light`/`dark`/`sepia` theme via a `data-theme` attribute.
- Components: `Onboarding` (first-launch 4-step wizard: welcome, name, quick-start surah picker, bismillah — see "Personalization" above), `Home` (dashboard: personalized greeting + context-aware message, progress summary, currently-memorizing shortcut, due-for-revision preview and bookmarked-ayat preview each capped at 3 with a link to their full screen, a settings-gear + help "?" link — falls back to a simple welcome screen with the same greeting when nothing is tracked yet), `SurahIndex` (114 surahs, searchable, filterable by status, color-coded; a "Select" toggle switches rows into a multi-select checklist with a floating "Mark memorized" bar, for bulk-confirming surahs already known — e.g. after onboarding, or a stack someone already had memorized before starting to track), `SurahDetail` (Arabic + per-ayah translation/tafsir toggles + `StatusControl` + a "Mark ayat" per-ayah range picker + a "Go to ayah" number search + a sticky, collapsible status/reading/practice panel + `NotesEditor` + the audio engine + test-mode/loop-range state), `RevisionScreen` (every surah with a `revision`-flagged range, ordered by longest-since-revised, with an inline "mark confident" action that only promotes the flagged ayahs), `Bookmarks` (`/bookmarks`: every bookmarked ayah, most recent first, each row deep-linking to its ayah via `?ayah=N`), `Settings` (`/settings`: name field, language picker, theme picker — the first UI for these, previously storage-only — + `SyncSettings`), `Help` (`/help`: a calm accordion of tips — not a guided overlay tour — covering status, ayah-range marking, bookmarks/go-to-ayah, audio, test-yourself, notes/tafsir, revision, and sync; reached via a "?" icon next to the settings gear on `Home`), `SyncSettings` (sync-code create/link/stop + `GoogleSignIn`), `GoogleSignIn` (renders nothing until configured), `AyahCard` (play button, per-ayah status dot, bookmark toggle, tafsir expand/collapse, test-mode hide/reveal, range-select tap target — all controlled by SurahDetail), `AudioPlayer` (play/pause/loading button), `StatusBadge`, `StatusControl`, `NotesEditor` (collapsible, debounced autosave), `BackButton` and `LoadingSpinner` (shared across every screen with a header/async load, extracted to cut duplication — see "Conventions" below).

## Audio: repeat and loop-range (`SurahDetail`)
One shared `<audio>` element, orchestrated in `SurahDetail` (not `AyahCard`, so only one ayah can ever sound at a time):
- **Single-ayah repeat**: tapping an ayah's play button repeats *that ayah* `settings.repeatCount` times (`1 | 3 | 5 | 10 | 'inf'`, cycled via the "Repeat ×n" chip). If every bitrate fails for that ayah, playback stops immediately rather than retrying the same broken URL on every remaining repeat.
- **Loop range**: the "Loop range" chip enters a selection mode — tapping two ayahs sets a start/end range (highlighted inline, with "Start"/"End" labels), then a floating bottom bar ("Looping ayah X–Y") plays that range in sequence, looping the whole range `repeatCount` times. A broken ayah inside a range doesn't stall the loop — playback just advances to the next ayah.
- Audio always stops (and range/test-mode state resets) on surah change and on unmount.

## Per-ayah status marking (`SurahDetail`, "Mark ayat")
A second tap-start/tap-end range picker, structurally identical to loop-range above but for setting a memorization status instead of playing audio — the two are mutually exclusive (entering one clears the other's selection). Unlike loop-range, tapping the same ayah twice commits a single-ayah range rather than resetting the selection, since flagging one specific ayah (e.g. Ayat al-Kursi) is a common target here. Once committed, a floating bar shows "Ayah X–Y" (or "Ayah N" for a single ayah) with four status pills (`New`/`Memorizing`/`Memorized`/`Needs revision`); tapping one calls `setAyahRangeStatus` and clears the selection. Each `AyahCard` also shows a small always-visible status dot next to its play button (via `getAyahStatus`), so per-ayah progress is visible while just reading, not only while marking.

## Bookmarks & jumping to an ayah
- `hifz:bookmarks` (`storage.js`) is a flat, sparse list of `{ surah, ayah, createdAt }` — one entry per bookmarked ayah, toggled via `toggleBookmark()`. It's a syncable key (`cloudSync.js` `SYNC_KEYS`); merging is a plain union deduped by surah+ayah (`mergeBookmarks`) rather than last-write-wins, since a bookmark isn't the kind of thing that should get overwritten by the other device — once either side has it, both should.
- Each `AyahCard` shows a small bookmark icon (outline, fills amber when active) next to its status dot; toggling it calls `toggleBookmark` and `schedulePush`. `Home`'s dashboard surfaces up to 3 recent bookmarks (falls back to nothing when there are none) with a link to the full `/bookmarks` list; a bookmark existing is now also enough to move the dashboard out of its empty-welcome state (`hasProgress` includes `bookmarks.length > 0`), since someone might bookmark ayat before marking anything memorized.
- Tapping a bookmark (from `Home` or `/bookmarks`) navigates to `/surah/:number?ayah=N`. `SurahDetail` reads that query param once the surah has loaded and calls the same `jumpToAyah()` used by the in-surah "Go to ayah" search — smooth-scrolls to the ayah and gives it a brief amber highlight (`highlightedAyah` state, cleared after ~1.8s). A `jumpedFromLinkRef` guards against re-jumping on re-renders; it resets on surah change.
- "Go to ayah" is a magnifying-glass icon in `SurahDetail`'s header (replacing the old spacer) that toggles a plain number input + "Go" button beneath the header; out-of-range or non-numeric input is a silent no-op rather than an error message, since the placeholder already states the valid range.
- Each `AyahCard`'s DOM node is registered into a `numberInSurah → element` ref map (`ayahRefs`, via a plain `cardRef` prop rather than `forwardRef`, since nothing else needed it) so both the search and the bookmark deep-link can call the same `scrollIntoView` + highlight logic.

## Sticky, collapsible status/options panel (`SurahDetail`)
`StatusControl` + a single merged row of Reading/Practice option chips are wrapped in a `position: sticky` panel (`top-[77px]`, matching the header's rendered height) rather than sitting in normal document flow, so they stay reachable without scrolling back to the top of a long surah (e.g. 286 ayat in Al-Baqarah) — tested by scrolling deep into a surah and confirming the panel stays pinned directly under the header with no gap. The Reading and Practice rows were originally two separately-labeled sections (`READING`/`PRACTICE` headers); they were merged into one unlabeled chip row after feedback that the panel felt cluttered — the chips' own text is self-descriptive, so the section labels were pure overhead. The header title itself is a plain (non-interactive) label — the toggle is instead a full-width chevron+text bar always sitting directly under the header: "Hide" at the bottom of the panel when open, "Show options" in its place when collapsed — and **both states use the same `sticky top-[77px]` treatment**, so the toggle bar itself stays pinned under the header even while scrolled and collapsed, not just when the panel is open. Same `optionsOpen` state, same screen position either way, so the control never has to be hunted for. Defaults open and resets to open on surah change. The `top` offset was hand-measured against the header's real rendered height and had to be corrected once already (85px → 77px, after the header shrank when its title stopped being an interactive button) — if the header markup changes again, re-measure rather than assume. `NotesEditor` and the "Go to ayah" search bar are deliberately left in normal (non-sticky) flow — notes are a one-off action, not something needed mid-scroll, and the ayah search closes itself right after a successful jump.

## "Test yourself" recall mode (`AyahCard`, driven by `SurahDetail`)
The "Test yourself" chip cycles **off → hide → first word → off**. In `hide`, the Arabic (and translation) are replaced with a "Tap to reveal" placeholder per ayah; in `firstWord`, only the ayah's first word is shown as a memory prompt. The play button stays visible in both — listening without seeing the text is a valid recall technique. Per-ayah revealed state resets automatically on mode change via a `key={ayah.number}-${testMode}` remount, not an effect. Test mode is session-only (not persisted) — it's a practice action, not a standing preference.

## Data model (per surah, with an optional per-ayah overlay)
`src/utils/storage.js`, key `hifz:surahStatus` — `{ [surahNumber]: { status, lastRevised, updatedAt, notes, ranges? } }`:
- `status`: `'new' | 'memorizing' | 'memorized' | 'revision'` — `isMemorizedStatus()` treats `memorized` and `revision` as both counting toward "memorized" progress (a `revision` surah is memorized, just flagged as needing review).
- `lastRevised`: set when status transitions **to** `memorized` (i.e. "I just confirmed this"). Flagging `revision` does *not* bump it — `RevisionScreen`'s "Mark confident" action calls `markRevisionConfident()`, which clears the flag(s) and bumps `lastRevised` in one call.
- `notes`: free-text tadabbur (reflection) text, edited via `NotesEditor` (`getSurahNotes`/`setSurahNotes`), autosaved ~400ms after the user stops typing.
- `ranges` (optional): a sorted list of non-overlapping `{ from, to, status }` spans (1-indexed ayah numbers within the surah, inclusive), for surahs whose progress isn't uniform — e.g. "just the last 2 ayat of Al-Baqarah are memorized." An ayah not covered by any range is implicitly `new`. **Most surahs never carry this** — `setAyahRangeStatus()` (called from `SurahDetail`'s "Mark ayat" range picker) collapses the result back to a plain `status` field whenever a range operation makes the surah uniform again, so the common whole-surah case stays as light as before.
  - `getAyahStatus(entry, numberInSurah)` reads a single ayah's effective status (ranges if present, else the whole-surah `status`) — used by `AyahCard`'s small per-ayah status dot and the audio/range UI.
  - `getMemorizedAyahCount(entry, ayahCount)` sums actual covered ayahs when ranges exist (used by `computeProgress()` for an ayah-accurate percent and by SurahDetail's "X of Y ayat memorized" caption), instead of the old all-or-nothing per-surah count.
  - The entry's top-level `status` is still kept in sync as a **derived summary** whenever ranges exist (via `deriveSurahStatus`): not fully covered → always `memorizing` (even if part of what's covered is flagged `revision` — a barely-started surah should never read as "done"); fully covered → `revision` if any range needs it, else `memorizing` if any range isn't confident yet, else `memorized`. This keeps every existing whole-surah consumer (the `SurahIndex` ring, dashboard counts, Juz completion) working unmodified.
  - `hasRevisionRanges(entry)` is a separate, more sensitive check used by `RevisionScreen` and the dashboard's due-for-revision list — it flags a surah the moment **any** range needs revision, regardless of whether the rest of the surah is fully covered, so a revision flag inside a still-partly-memorized surah isn't hidden behind the (stricter) derived summary status.
  - A whole-surah action (`setSurahStatus`, used by `SurahIndex`'s bulk multi-select and `Onboarding`'s quick-start) is a deliberate override — it always clears `ranges`.
  - Juz completion (`computeProgress()`) checks each ayah's own status via `getAyahStatus` against the `surah:ayahInSurah → page` index, so a surah straddling a Juz boundary — or only partly memorized on one side of it — no longer falsely marks that Juz complete.

No daily-activity/streak log has been built. Tilawah's streak mechanic is
explicitly a habit-tracking device; Hifz's philosophy is "no guilt-tripping,"
so that shape of feature needs a deliberate go/no-go, not a silent port.

## Conventions
- Themes via CSS variables (`light`/`dark`/`sepia`) in `index.css`; `paper`/`emerald`/`amber`/`clay`/`muted` Tailwind colors map to them. Applied pre-paint by an inline script in `index.html`.
- Palette: emerald primary (`--c-emerald`) + amber accent (`--c-amber`) — a sister palette to Tilawah's navy/gold, not a clone. Same warm-paper base surface. `clay` (soft terracotta) was added in phase 2 purely as a fourth status color (revision-needed) — it's a functional/status token, not part of the core brand pair.
- All settings live in `DEFAULT_SETTINGS` (`storage.js`).
- Every screen's header uses `BackButton`; every full-screen async load uses `LoadingSpinner` — reuse these instead of re-inlining the SVG/spinner markup (they were extracted from 7 and 4 near-identical copies, respectively).
- After changes: `npm run build` to verify; commit; push to the working branch.
